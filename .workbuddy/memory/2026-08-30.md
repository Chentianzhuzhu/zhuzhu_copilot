## 无响应根因定案 + 真人化改造（commit 8004274）

- `POST /api/v0/chat_session/create`（创建会话 ✓）
- `POST /api/v0/chat/completion`（聊天请求，**返回 200** ✓）

## ★ 真正根因：窗口隐藏导致 visibilityState=hidden（commit a291353）
用户质疑"是不是隐藏了浏览器主窗口的原因"——**完全正确，实测定案**：

**决定性对比实测**：
- 窗口移出屏幕（-32000）：`visibilityState=hidden` → 45s 无回复（SSE 回复挂起，WIP token 恒 0）
- 窗口移到屏幕内：`visibilityState=visible` → **2s 出回复**

**机制**：Chromium 对窗口不可见（offscreen）页面置 `document.visibilityState=hidden`，页面 JS 整体降级——DeepSeek 的 SSE 流式回复处理被挂起。此前加的 `--disable-background-timer-throttling`/`--disable-renderer-backgrounding` **不覆盖 visibilityState 机制**，窗口必须真正可见。之前的"风控/限流"判断是误判——隐藏才是无响应真因。

**修复**：窗口保持可见但最小打扰——**屏幕右下角小窗**（640x480，读 `screen.availWidth/Height` 定位），`visibilityState=visible` + 用户几乎感知不到。

**验证（真实浏览器 e2e）**：
- 右下角小窗 `visibilityState=visible`，**首条回复 1s**（此前 hidden 45s+）
- **工具调用全链路通过**：模型输出文本协议 JSON → 代理转 `tool_calls` → `list_directory` 真实执行（列出桌面 53 项）→ 结果回传 → 模型正常续答

**结论**：DeepSeek 网页版 + 文本协议工具调用全链路已打通且秒响应。重要经验：**CDP 驱动网页交互时窗口必须保持可见（visibilityState=visible），否则页面 JS/SSE 处理被 Chromium 降级挂起**——隐藏窗口需同时确认页面 visibility，且该机制不受 timer-throttling 参数覆盖。
