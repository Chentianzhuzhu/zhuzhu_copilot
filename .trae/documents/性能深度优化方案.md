# 性能深度优化方案：长文本输出 / 启动速度 / 响应与并发

## Context（为什么做、要达到什么）

项目为 PyQt6 桌面 AI 助手（主代码 `src/zhuzhu_Copilot/`）。用户要求深度优化三件事：**Agent 长文本输出性能、应用响应/启动速度、Agent 长任务流并发性能**。

调研结论（已读代码确认，避免重复劳动）：

- 引擎每轮热点此前已优化过：`scripts/_probe_longtask_perf.py` 记录 409ms/轮 → 14.5ms/轮（`_all_tools` 的 schema 深拷贝已进程内缓存、技能覆盖查询已缓存、`_system_prompt` 已对比不覆盖），且 `tests/test_longtask_perf.py` 已守护这些缓存契约。**本轮不再重复优化这些点。**
- 聊天气泡已具备增量渲染 + 高度测量缓存（`_label_hfw` / `ChatTurn.relayout_heights`）+ 落字节奏（`_reveal_*`），并有 `tests/test_stream_reveal_pacing.py`、`tests/test_ui_longtask_fluency.py` 守护。**沿用这些机制，不另造轮子。**
- 子 Agent 已并行（`agent_subagent.run_parallel`，`SUB_AGENT_MAX_WORKERS`）、工具并发编辑已有 `ThreadPoolExecutor`（`agent_engine.py` L2243）。

因此本轮聚焦**尚未覆盖的三类瓶颈**：

1. **逐字吐字下的长文本输出**：上游逐 token 回调时，每个增量都会 `evt_signal.emit` 一次跨线程 Qt 信号、走一遍 `_on_delta`（含每 chunk `_scroll_bottom()`），且 `self._segments[-1]["raw"] += s`（[agent_panel.py](file:///c:/Users/zhuzhu/Desktop/my%20first%20android%20app/src/zhuzhu_Copilot/ui/agent_panel.py#L20578-L20591)）在 dict 值上的 `+=` 无法走 CPython 就地扩容，最坏情况是 O(n²) 字符拷贝。
2. **启动**：模块预热线程在 splash 关闭后才启动（[main.py](file:///c:/Users/zhuzhu/Desktop/my%20first%20android%20app/src/main.py#L505-L523)），本可与 2 秒启动动画并行；且无启动阶段计时基线。
3. **响应/并发**：LLM 客户端为每次请求新建 TCP+TLS 连接（urllib，`_chat_stream_once`，[agent_llm.py](file:///c:/Users/zhuzhu/Desktop/my%20first%20android%20app/src/zhuzhu_Copilot/core/agent_llm.py#L1843-L1900)），长任务每轮多付几十~几百 ms 握手；缺启动/流式/多会话并发的性能基线探针。

## 用户已确认的范围决策

| 决策项 | 结论 |
| --- | --- |
| 启动动画 | **保持固定 2 秒**，不改启动时序；只做「预热提前并行」等无感知优化 |
| 流式增量合批 | **接受**（引擎侧 ~16ms 合批后推送界面，落字观感由现有节奏层保持不变） |
| 连接复用池 | **允许**（仅标准库实现，异常自动回退，可配置开关） |
| 长会话首屏分批渲染 | **允许，但仅在实测确认是瓶颈时才做** |

## 阶段 1：长文本输出优化

1. **引擎侧增量合批**（[agent_engine.py `_on_stream_delta`](file:///c:/Users/zhuzhu/Desktop/my%20first%20android%20app/src/zhuzhu_Copilot/core/agent_engine.py#L1452-L1458)）
   - 新增小聚合器（类 + 模块级常量：`_DELTA_FLUSH_MS = 16`、`_DELTA_FLUSH_CHARS = 512`），累积增量后一次性调用 `self.on_delta`。
   - **边界强制 flush**：回合结束、工具调用开始、停止、异常路径必须 flush，保证一个字不丢、顺序不变；TTS 句子切分（`_tts_buf`）逻辑不动。
   - 面板侧回调签名不变，`evt_signal` 发射频率因此从「上游 token 速率」降到 ≤ ~60Hz。
2. **UI 每 chunk 微开销削减**（[`_on_delta`](file:///c:/Users/zhuzhu/Desktop/my%20first%20android%20app/src/zhuzhu_Copilot/ui/agent_panel.py#L20578-L20591)）
   - `_scroll_bottom()` 按时间节流（≥30ms 一次，常量可配）；其余路径已 O(1)，不动。
   - 高度测量沿用 [`_label_hfw`](file:///c:/Users/zhuzhu/Desktop/my%20first%20android%20app/src/zhuzhu_Copilot/ui/agent_chat_bubbles.py#L291-L315) 缓存与 `_seg_sig` O(1) 签名，不新增机制。
3. **（阶段 0 数据决定）** 若单段超大文本（>10 万字）渲染仍是主线程大头：仅扩展既有 `_STREAM_BIG_CHARS` 分级节拍或对该段做增量 HTML 拼接，不重构渲染层。

## 风险与规避

| 风险 | 规避 |
| --- | --- |
| 合批后到达粒度变粗 | 已确认接受；落字节奏层不变，末尾强制 flush |
| keep-alive 半开连接 / SSE 未读完复用毒化连接 | 仅在响应完整读完或显式关闭后归还；异常一律丢弃重建 + urllib 回退 |
| 连接池多线程共享 | 每 key 每线程独占取用、用后归还；锁只保护取还，不持锁等待 IO |
| 启动改动引入时序回归 | 只提前预热线程，不动 splash 2 秒时序与 onboarding 顺序；保留现有 splash/onboarding 测试 |

## 实施结果与决策偏差记录（收尾）

**阶段 1 偏差（方案被数据否决）**：原定「引擎侧 ~16ms 增量合批」经探针实测收益仅 ~1%（面板侧已有落字节奏层，信号频率不是瓶颈），属过度设计 → 改为**流式单帧成本自适应节拍**（`_STREAM_TICK_BIG_MS=60` / `_STREAM_DUTY_TARGET=0.25` / `_STREAM_TICK_MAX_MS=200` / `_STREAM_COST_DECAY=0.8`，agent_panel）：大帧时自动放慢 tick、按单帧实测成本调节，落字观感不变。故 `tests/test_stream_delta_coalesce.py` 未新增（合批未实施），由既有 `test_stream_reveal_pacing.py` / `test_ui_longtask_fluency.py` 守护。

**引擎每轮热点（探针 `_probe_longtask_perf.py`，120 轮）**：47.4 → **16.8 ms/轮**（2.8×）。主项 `_estimate_tokens`（每轮 4 次全量重算，含 C 层正则扫全文）按消息对象身份缓存（content/tool_calls 引用比对失效，`_EST_CACHE_SLACK` 有界清理）：3.344s → 0.107s（31×）；`_load_module` 双次 stat 改单次。新增 4 项缓存契约测试（`test_longtask_perf.py`）。

**阶段 2 实测（`_probe_startup_perf.py --sim`）**：「动画结束 → 界面可见」关键路径 887.5ms（含 350ms 首帧窗口，构造约 540ms）；预热线程（import agent_panel + PBKDF2 解密）在固定 2s 动画窗口内完成（常规表 import/解密全部 0.0~0.1ms 命中）。已知取舍：`prewarm_copilot_panel`（浮层构造，Qt 必须主线程，1.4~3s）改为面板首帧后 600ms 触发 —— 由原「关闭动画后空屏等」变为「界面可见后再执行」，时序与启动行为不变。

**阶段 3 实测（`_probe_concurrency_perf.py`，真实 API 3 路会话 × 3 轮）**：9 次请求仅新建 **3 条连接**（6 次复用）；第 1 轮 ~730ms（含 TCP/TLS 握手），后续轮 ~340-400ms；并发墙钟 5242ms < Σ延迟 8184ms（池锁只保护取还、不持锁等待 IO，未串行化）。单元测试：`tests/test_agent_http_pool.py`（11 项，本地 ThreadingHTTPServer 真实 socket：复用/回收/上限/早关丢弃/HTTP 错误体/开关与代理回退/死连接自愈/LLM 流式解析集成/stop 断开）。偏差：原计划的 `test_llm_stream_pool_fallback.py` 合并进同一文件（transport 与消费方契约共用一套本地服务器，避免重复搭建）。

## 第二轮：长对话切换加载 + 长任务每轮流（探针驱动）

**长对话切换（`scripts/_probe_switch_perf.py`，真实会话副本，A/B 同数据）**：切到 1.36MB / 194 个过程块的会话，主线程阻塞 **1921 → 812ms**（内存态命中）、**2748 → 1423ms**（首次读盘）。
根因（微探针 + cProfile 定位）：历史回合里**隐藏**过程块的内层输出标签首次 `setVisible` 会触发整篇富文本排版（2000 字符 ≈20ms、2 万字符级可达百毫秒）——单块内容填充 9.5ms 中约 4.2ms 花在这一句，上百块累积成秒级白屏。
做法：历史回合（done）新建过程块的「内层可见性收尾」推迟到事件循环空闲分片执行（`_IdleSpreader`，每片 ≤6ms；展开时 `ChatTurn._resume_deferred()` 同步补齐；流式回合不推迟）。切换路径单块填充 9.5 → **0.58ms**；空闲铺完约 1.3s（不阻塞交互）。测试：`tests/test_history_deferred_show.py` 4 项。

**长任务每轮（`scripts/_probe_longtask_perf.py`，120 轮）**：18.0 → **13.9 ms/轮**（上一轮 47.4 → 16.8ms/轮 的基础上继续）。热点是「每轮重复 stat」：Windows 单次 stat ≈0.5ms（杀软），而每轮要多次解析激活工作流/存在性/元数据/子 Agent 注册表/数据目录。
- `agent_workflow`：短 TTL 指纹缓存（`file_fingerprint`，含 mode）+ `active_workflow` 解析缓存，写入侧全部显式失效（应用内改动仍即时生效）。隔离实测 `active_workflow` 1.21→**0.002ms**、`is_workflow` 2.46→0.11、`tool_schemas` 2.41→0.12、`registered_subagents` 2.36→0.06。
- `app_identity.data_root`：按家目录缓存（0.65→~0.02ms）；`agent_skills.settings_view`：只读免拷贝视图（`cap_enabled` 7 次/轮）。
- 刻意保留 `_load_module` 逐次 stat：`agent.py`/`tools.py` 热更新即时生效（既有契约测试钉住）。
- 循环实测：`_all_tools` 2.88→0.61ms、`_sync_skill_msg` 0.25→0.09ms、`_system_prompt` 4.27→3.49ms。测试：`tests/test_hot_path_caches.py` 8 项。

**已知遗留（非本次改动引入）**：`tests/test_builtin_workflow.py` 单独运行时会以 0xC0000409 崩溃（在 HEAD 干净工作树复现，全套运行不受影响），属既有 Qt 用例的独立运行问题，待另案处理。
