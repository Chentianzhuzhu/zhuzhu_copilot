一、核心结论
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

该部署架构整体可行，采用"Cloudflare Pages（前端）+ 自建云服务器（后端）+ Nginx 反代 + Redis 缓存"的主流方案，但需在配置层面规避几个关键风险点。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
二、主要技术要点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【1. 真实 IP 获取】
问题：CF 代理下后端只能看到 CF 的 IP
解决：读取 CF-Connecting-IP 请求头，Nginx 配置 set_real_ip_from
注意：CF IP 段会变动，需定期更新或使用自动同步工具

【2. CDN 缓存策略】
问题：API 响应易被误缓存，导致脏数据
解决：
  • 对 /api/* 路径设置 Edge Cache TTL: 0 或 bypass
  • 响应头加 Cache-Control: private, no-store
  • 避免使用 no-cache（易被误解）

【3. 超时风险】
问题：CF 默认超时 100 秒，慢查询会触发 524 错误
解决：调大超时时间或改为异步/分片处理

【4. Nginx 配置陷阱】
问题：proxy_pass 使用 $http_host 会导致重定向循环
解决：显式设置 proxy_set_header Host $host

三、推荐部署顺序
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1️⃣ 先部署云服务器 + Nginx（不开 CF 代理），验证接口
2️⃣ 接入 CF，开启 CDN 前将 API 路径设为 bypass
3️⃣ 逐步放开静态资源缓存规则，观察后微调

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
四、Redis 持久化方案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

推荐混合模式（RDB + AOF）：
  appendonly yes
  appendfsync everysec
  no-appendfsync-on-rewrite yes
  maxmemory-policy volatile-lru

优势：兼顾性能与安全，重写期间不阻塞写入
风险：大内存场景 fork 子进程可能 OOM

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

• 部署后持续监控缓存命中率、API 响应时间、错误率
