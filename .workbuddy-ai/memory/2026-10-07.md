### 三、登录回跳根因与修复（关键）
- **根因**：登录页是 **HTTPS**（`https://chentian.dpdns.org/authapp/...`），
  回调是 `http://127.0.0.1:18765`。`fetch` 属**子资源请求**，被浏览器
  **混合内容 / 私有网络访问（PNA）** 策略拦截，`mode:'no-cors'` 也无法绕过 →
  源码运行时 token 送不回来。
- **修复（双通道+兜底）**：
  - A 主通道：登录页把结果 `POST /api/auth/login_result`，客户端轮询取回（**不受本地策略影响**）；
  - B 快通道：`window.location.href = http://127.0.0.1:…`（**顶层导航**不受混合内容限制）；
  - C 兜底：手动复制 token。
- 登录页 `static/login/index.html` 新增 `relayToServer` / `probeLocalCallback` / `buildCallbackUrl`，
  `showManualCopy(token, relayOk)`。

### 二、推送丢失（task28）✅ 根因：**多 worker 内存连接表**
- 线上 `uvicorn --workers 2`，每个 worker 独立进程 → **各自的 `ws_manager.active_connections`**。
  管理端 HTTP 落到 worker B、而用户 WS 挂在 worker A 时，B 本地查表为空 → **静默丢弃**。
  （`journalctl` 证据：WS 连接在 PID 1766659，`batch/membership` 请求在 1766658。）
  症状即「有时推得出去、有时推不出去」；`verify_ws_new_features.py` 复现：
  `announcement`+`points_update` 到达、`membership_update` **丢失**。
- 修法：**Redis pub/sub 中转**（`app/services/ws_manager.py` 重写）
  - `send_to_user`/`broadcast` → `PUBLISH zhuzhu:ws:broadcast`（信封 `{kind:user|all,...}`）；
  - 每 worker 启动一个订阅端（`start_subscriber`，`main.py` lifespan 拉起/关闭），
    收到即在**本进程** `_deliver_local` / `_deliver_local_all`；
  - 在线状态用 Redis 集合 `zhuzhu:ws:online:{uid}`（成员=WORKER_ID，TTL 120s，
    连接/心跳续期、断开移除）；`is_online` / `count_online(user_ids)` / `total_online_connections`
    提供**跨 worker** 在线统计（推送计数改用此值，不再用本进程投递返回值）；
  - Redis 不可用 → **降级本地直投**（单 worker/开发环境不炸）；
  - `_chunked_push` 改为推送后取 `count_online` 作为 `pushed`。
- **坑1**：全局 Redis 客户端 `socket_timeout=5`，`pubsub.listen()` 空闲 >5s 被判读超时 →
  每 ~5s 断连重连（日志刷 `Timeout reading from 127.0.0.1:6379`）。
  修：`redis_client.make_pubsub_client()` 专用客户端 `socket_timeout=None` +
  `health_check_interval=30`；订阅端用它。
- **坑2**：`stop_subscriber` 里 `except Exception` **抓不到** `asyncio.CancelledError`
  （3.8+ 它继承 `BaseException`）→ 关闭时抛到调用方。已显式 `except asyncio.CancelledError: pass`。
- **坑3**：`asyncio.CancelledError` 与 `_publish` 里 `from ... import redis as r` 的局部作用域，
  统一改为 `_get_redis()`（已注入实例直接复用，便于测试替身）。
- 新增文件：`scripts/verify_ws_multworker_relay.py`（本地假 Redis 驱动两个 WSManager 模拟双 worker）、

## 公告轮询「发布后仍不生效」根因定位与修复（第八批）

### 现象
用户反馈：加了公开 API + 轮询，**发布后仍轮询不到公告**。

### 根因（两个独立问题）
1. **客户端启动顺序 Bug（真因）**：`ui/agent_panel.py`
   - `_build_auth_user_bar()` 在 **14808 行**调用，而 `_announce_label` 在 **14813 行**才创建；
   - 而 `start_ws_if_logged_in()`（进而 `start_announcement_polling()`）当时是挂在
     `_set_announcement()` 末尾的 —— 该方法开头 `if lbl is None: return` **提前返回**，
     启动瞬间 lbl 还是 None → **调用链被吞**，轮询定时器从未创建。
   - 用 `git show HEAD:...` 做 AST 对比确认：修复前 `_build_auth_user_bar` 与 `_set_announcement`
     对 `start_ws_if_logged_in` 的调用数**都是 0**（即启动路径完全没有接线）。
2. **发布产物过期（叠加因素）**：`dist/zhuzhu Copilot Setup.exe` = Oct 6 16:04、
   `dist/zhuzhu Copilot/zhuzhu Copilot.exe` = Oct 6 15:53，最新构建日志 Oct 6 15:45 ——
   均**早于**本轮代码；打包 exe（PyInstaller onefile）内不含新符号。**必须重新打包发版**。

### 修复
- `ui/agent_panel.py` `_build_auth_user_bar`：在 `_refresh_auth_user_widget()` 之后
  **直接**调用 `auth.start_ws_if_logged_in()`（不再依赖 `_set_announcement`），
  并附注释说明「公告标签在本方法之后才构建」的坑；
- 移除 `_set_announcement()` 末尾的 `start_ws_if_logged_in()`（消除误导来源）。

### 验证
- `scripts/verify_announcement_startup_order.py`（新建，AST + 运行期，8 项）：
  修复点1/2、提前 return 仍在、启动后定时器 30000ms、启动即首拉 →
  **STARTUP_POLL_ORDER PASS**。
- `scripts/verify_announcement_poll.py` 复跑 → **ANNOUNCEMENT_POLL PASS**。

### 关键结论（重要）
- **客户端改动必须重新打包 + 发版才会生效**——排查此类「改了源码但线上没变化」的问题时，
  先核对 `dist/` 产物与 `build/*.log` 的时间戳是否晚于最后一次源码修改。
- 打包加固：`core/*.py` 经 Cython 编译为 `.pyd`（`scripts/cython_build.py`），
  `ui/*.py` 保留为可读 `.py` 但 PyInstaller 会收集进 PYZ；因此 exe 内**无明文符号**，
  不能靠 grep exe 字符串判断是否包含新代码，应比对时间戳或构建日志。
- 启动接线不要挂在「可能因 precondition 提前 return」的函数里；应放在明确的构建入口。
