# 2026-10-12

## computer-control 插件（第七轮）：修复「应用在后台/最小化时疯狂调用工具查找位置」

**用户反馈**：复杂任务（打开微信 → 给第二个人发你好 → 把桌面文件发给第三个人 → 引用他说的话）
做不了，而且「微信在后台、或者微信就在任务栏底部时，agent 还疯狂调用工具查找位置」。

### 根因（两条，缺一不可）

1. **插件里根本没有「启动应用」的能力**：`list_windows` 只能看到**已经在跑**的窗口。
   微信没启动时，模型没有任何工具能把它打开 → 只能反复 `list_windows` / `screen_shot`
   / `manage_window` 地找，这就是「疯狂调用工具」。
2. **技能规范没告诉模型该怎么做**：没有「先 open_app，不要自己找窗口」这条纪律，
   模型自然会用最直觉的方式（反复列窗口）去试。

### 修掉的真实缺陷（都是实测确认过的）

1. **`_raise_topmost` 一直抛 NameError，窗口被永久留在 always-on-top**（最严重）：
   函数里用了裸名 `WS_EX_TOPMOST`，但该常量**定义在 uia.py**，server.py 里没有 →
   一执行就 `NameError`，被 `except Exception` 吞掉。后果有两层：
   - 「取消置顶」那一步**从未执行** → 用户窗口被永久钉在最前面，再也压不下去；
   - 函数返回 False → 调用方（`_ensure_click_target` / `_ensure_input_target`）
     以为「临时置顶也失败了」，于是报「已拒绝点击」。
   修法：在 server.py 里自己定义 `WS_EX_TOPMOST`，并把「取消置顶」放进 `finally`，
   保证**无论置顶成功与否都撤销**；另加 `_ex_style()`（uia 不可用时退回
   `GetWindowLongPtrW`，且显式声明 restype=c_ssize_t，避免 64 位截断）。
2. **`activate_window` 的 `AttachThreadInput` 接错了线程**：原来接的是
   **目标窗口的线程**，但前台锁判定的是「调用线程的输入队列是否与**前台窗口**的线程相连」
   → 这一步形同虚设，`SetForegroundWindow` 被系统静默拒绝。这正是「窗口在后台时
   怎么都切不到前台」的根因之一。修法：同时接**前台窗口的线程**与目标窗口的线程。

### 新增能力

- **`open_app(name)` —— 一次调用完成「找窗口 → 没运行就启动 → 等窗口 → 恢复最小化 →
  置顶 → 实测校验」，并直接返回 hwnd**。这是本次修复的核心。
  - 应用索引：**开始菜单 `.lnk`（用户+全局）+ 注册表 `App Paths`**，零第三方依赖、
    零 COM（`.lnk` 交给 `ShellExecute` 自己解析，不需要读快捷方式内容）。本机 119 项 / 0.10s。
  - 系统目录探测兜底：`calc`/`taskmgr`/`notepad` 这类**既无快捷方式也不在 App Paths**
    的系统工具，按名字探 `System32`。
  - UWP：`设置` → `ms-settings:` 协议 URI。注意**盘符 `C:\…` 也匹配 `^[a-z]:`**，
    必须先排除再判 URI，否则启动目标会绕过存在性校验。
  - 启动后若名字对不上（启动器/启动台），兜底认「启动后新出现的窗口」并**如实标注**。
  - 找不到时**列出最接近的已安装应用名**，让模型一次改对，而不是反复猜。
- `manage_window` 新增 `focus` 动作（= `_bring_to_front`）；`activate` 也改用同一套
  「恢复 → 置顶 → topmost 兜底 → 实测校验」。
- `list_windows` 每行直接标注**「最小化」**：最小化窗口的矩形是哨兵值
  `-32000,-32000,160,28`，模型照着算坐标会全在屏幕外（实测确认过这个值）。
  `manage_window(action="state")` 改为复用 `list_windows` 的同一套渲染，避免两种格式。

### SKILL.md（修复的另一半）

- 新增 **「第 0 步永远是 open_app：不要「找窗口」」** 一节，直接写出错误示范循环，
  并说明为什么 open_app 就够（能启动没运行的、能恢复最小化的、会实测校验、直接给 hwnd）。
- 标准流程第 2 步从 `list_windows` 改成 `open_app`。
- 新增 **坑 1.9「不要自己找窗口」**：同一失败动作不要连试两次以上。
- 新增 **「复杂任务剧本：微信（发消息 → 发文件 → 引用消息）」**，逐步可验证：
  `open_app` → `list_rows` 数第 N 行（**给了名字就优先用搜索框，比数行可靠**）→
  发消息（注意 Enter 还是 Ctrl+Enter）→ 发文件（**不要拖图标**，走文件对话框输完整路径）→
  引用（右键消息 → `list_menus` → `click_element("引用")` → 输入 → 发送）。

### 验证

- `tests/test_computer_control_plugin.py` 新增 **18 个用例**，共 **98 个全绿**
  （索引/别名打分/URI 判定/启动目标校验/`_raise_topmost` 三种撤销路径/
  `_ex_style` 在 uia 缺失时可用/`activate_window` 必须接前台线程/
  SKILL.md 必须保留 open_app 纪律）。
- 真机端到端（用记事本做靶，已清理）：启动 → 找到 → 切前台；再调 → 认到已在运行；
  最小化后 → 自动恢复 + 切前台；`list_windows` 正确标注「最小化」。
- **本机没装商店版「计算器」**，所以 `System32\calc.exe`（UWP 转发壳）启动后
  什么都不会发生 —— 这是环境事实，不是缺陷；错误信息里已把这种情况写明。

## 元素坐标计算算法优化（第八轮）：像素级元素吸附 + 精确换算

### 用户需求

「还是无法精确点击屏幕元素，请优化元素坐标计算算法，使其能帮助用户完成各项复杂操作，
包括剪辑软件 blender 建模等专业软件」。

### 关键推理：删掉 UIA 之后，误差只剩三个来源

上一轮把元素树整个删了，agent 变成**纯坐标**。于是「点不准」的误差**全部**来自点击之前：
① 截图 → 物理坐标的**换算数学**；② 截图的**矩形范围**（多屏/DPI）；
③ 模型**估**像素位置的能力。这一轮三个都打，而不是只调算法。

### 1. 换算数学：截断 → 四舍五入

- 旧代码 `int(x * w / iw)` 是**截断**。缩放比 1920→1280 = ×1.5 时，
  截断产生**系统性负偏**，且越往右下越大，最大可达一个缩放步长（4K→1280 时 3px）。
- 改成 `int(round(...))`，误差从「单向累积」压到 **±0.5px**。
- 注意 Python 的 `round()` 是**银行家舍入**（`round(4.5)==4`），所以测试用例
  用 `x=1`（1.5→2）和 `x=5`（7.5→8），不能用 4.5。外层 `int()` 也不能省 ——
  裸 float 会让 SendInput/GDI 的 argtypes 报错。

### 2. 截图范围：主屏 → 虚拟桌面

- `SM_CXSCREEN` 只给**主显示器**。注入侧用 `MOUSEEVENTF_VIRTUALDESK` 按
  **虚拟桌面**（`SM_XVIRTUALSCREEN`/`SM_YVIRTUALSCREEN`/`SM_CXVIRTUALSCREEN`/
  `SM_CYVIRTUALSCREEN`）归一化。两边矩形不一致 → 副屏目标整体偏移一个虚拟原点。
- 现在 `grab_screen` / `grab_zoom` 的钳位 / `_region_snapshot_at` / 注入
  **四处都统一到虚拟桌面矩形**。`grab_screen` 从返回 5 个值改成 **7 个**
  （多了虚拟原点 `ox, oy`），`screen_shot` 全屏分支据此提示。

### 3. 核心新算法：像素级元素吸附（`_snap_to_element`）

删掉元素树后，精度全押在「模型估的像素」上。补回精度但**不碰控件树**的办法，
就是对截图做**纯像素**分析 —— 这也正是 Blender/CAD/剪辑软件唯一可行的路
（这类界面是 GPU 自绘，根本没有 accessibility tree）。

算法（在估计点周围 `reach` 半径内做 1:1 区域截图）：

1. **背景色** = 区域**四条边框环**上的**众数颜色**（量化到 8 级再取平均）。
   用边框而不是全图，是为了让「大面积按钮/画布」不会把自己当成背景。
2. **前景连通域** = 4 邻接连通域标记，判定条件是「与背景的颜色距离 > `SNAP_BG_DIST`」。
3. **四道独立拒绝条件**：面积 < `SNAP_MIN_AREA`；面积 > 区域面积 ×
   `SNAP_MAX_AREA_RATIO`（0.55）；宽或高 < `SNAP_MIN_SPAN`；
   **bbox 贴到区域边界**（真实尺寸未知 ⇒ 中心不可信）。
4. 取**离估计点最近**的连通域，点它的 **bbox 中心**。

**颜色距离为什么能合并按钮和按钮上的字**：按钮填充和字色不同，但 4 邻接连通会把
它们连成**同一个连通域**，bbox 恰好就是整个按钮 —— 真正分隔相邻控件的是
**背景缝隙**，不是颜色。

**两道独立的位移闸门**（设计上的一次修正）：
① 估计点到候选 bbox 的距离 ≤ `reach/2`（候选必须**确实在附近**）；
② 最终位移 ≤ `reach`（大元素的中心可能很远）。
只留 ② 会拒掉「估计点落在按钮边缘、中心在 40px 外」这种**最该吸附**的情况。

**阈值标定**：`SNAP_BG_DIST = 18`（≈每通道 6 级），**不是 30** ——
Blender 这类界面按钮填充与面板底色只差约 10 级。放宽带来的误报风险，
由「贴边拒绝 + 面积上限 + 两道位移闸门」兜住。实测 10 级可检出、4 级不检出、
渐变和椒盐噪声都不误报。

**复杂度**：96×96 区域上全标记实测 **~6.6ms**，远低于被删掉的 UIA 树那 3s 预算。

### 4. 新增 `refine_point` 工具（第 23 个）

返回 `[text, image]`：先吸附，再把「估计点」和「吸附点」**画在同一张放大图**上
（黄十字 `估` / 绿十字 `吸附`），让模型**看一眼就能确认**，不用靠猜。

### 5. 最近邻放大（专业软件读数的前提）

- `_stretch_mode(enlarging, smooth)` 抽出来单独可测：
  **放大**且不要求平滑 → `COLORONCOLOR`(3)（逐像素复制，1px 边框放大 3 倍仍是 3px 实边，
  图像像素 ↔ 屏幕像素 1:1，**读数即坐标**）；**缩小** → `HALFTONE`(4)（插值，
  避免最近邻丢像素）。`grab_zoom` 默认 `smooth=False`（清晰）。
- 这条对 Blender 尤其关键：1280 宽的整屏图上 1px 可能等于屏幕上 3px，
  而 Blender 的按钮才 20px 高 —— 必须先放大到 1:1 再读数。

### 6. 如实报告换算

新增 `_transform_line()`，每张截图元信息里都印出换算公式，例如
`(0,0) + 图像坐标 × (1.5000,1.5000)`，并提醒「图上 1px ≈ 屏幕 1.50px，
读数误差会被放大 1.50 倍，小目标请先 zoom_in」。scale≈1 时说「即 1:1」。

### 7. `space="screen"` 逃生门

模型经常手里已经有**物理**坐标（上一次返回值、`list_windows` 的位置），
没有逃生门就必须重新截图来重设基线，而新截图可能又换了窗口/区域。
`space` 接受 `screen`/`physical`/`abs`/`absolute`/`物理`/`绝对`，直接跳过换算。

### 接线

- `click`/`click_window`/`long_press`/`drag`（两端都吸附）默认吸附，`snap=false` 可关，
  `snap_reach` 可调；`swipe`/`select` 默认**不**吸附（`default_on=False`）；
  所有 note 经 `_join_notes` 汇总。

### SKILL.md / plugin.json

- 核心原则「四步闭环」→ **「五步闭环」**：看 → 量 → **修(`refine_point`)** → 点 → 验。
  并写明「估计为什么必然有损」（1280 宽图 1px=4K 上 3px，而 Blender 按钮才 20px 高）。
- 新增 **「点不准怎么排查（坐标精度手册）」**：症状→病因→处方 5 行表；
  「吸附什么时候要关掉」（内容区/像素级精确/吸错邻居 三种）；
  「吸附为什么是安全的」；坐标系与换算（`space="screen"` + 打印的换算公式）。
- 工具速查表重建，加上 `refine_point` 与四个新参数。

## 列表点击精度修复（第九轮）：横向内容带 + 行标尺

### 用户反馈

「点击元素的精准度还是不行，比如点击微信联系人列表，它总是会点偏」。

### 先复现，再动手（这一步是关键）

在改算法之前，先用**合成微信联系人列表**（头像 + 名字笔画 + 行分隔线，行高 64px）
跑探针，拿到事实。结论是**两个根因，都不是「算法不够聪明」**：

1. **估计点落在行的空白区 → 完全不吸附**。微信一行几百像素宽，内容（头像/名字）
   只在左边。搜索半径 48 → 区域只有 96px 宽，够不着内容 → 连通域为空 →
   `_snap_to_element` 直接放弃、原样返回。**模型还得不到任何提示**（note 为空）。
   实测：`est_x=190` 时 dy 从 0 到 48 全部「无吸附」。
2. **有内容时只吸到单个汉字**（15×15），而不是「行」。垂直容差只有半个字高。

根因是同一个：**算法只懂「离估计点最近的连通块」，没有「行」的概念。**

### 修法：横向内容带（`_fg_bands` + `_pick_band`）

区域按 y 做前景投影 → 切出一条条横向内容带 → 估计点所在的那条带就是它的「行」，
**y 对齐到该带中心**。关键设计取舍：

- **只动 y，不动 x**。列表整行可点，保持原 x 最安全；而**工具条上并排的按钮**如果按
  整条带的 x 中心吸附，会点到**隔壁按钮** —— 这是必须避免的回归（已写成测试护栏）。
  x 仍取「同一条带内离估计点最近的连通域中心」，距离按外接矩形算（点在框内即为 0），
  所以大元素不受影响，只有估计点在元素**之外**时才受 `near_cap` 约束。
- **搜索半径 48 → 88**（区域 176×176）。这是被列表逼出来的：内容离估计点可能很远。
  代价 38.6ms/snap（旧 18.5ms），远低于 3s 预算。
- **四个新常量**：`SNAP_BAND_MIN_PIXELS=3`、`SNAP_BAND_MERGE_GAP=5`（汉字横笔画之间
  有空隙，「三」会断成三条，5px 能并回一个字又远小于行间距）、
  `SNAP_BAND_MAX_RATIO=0.62`、`SNAP_BAND_MIN_SPAN=6`。
- **两条拒绝条件**（宁可退回连通域逻辑也不乱动）：带高 > 区域高 62% ⇒ 是**连续内容**
  （Blender 视口/画布/整块面板），按它的中心吸附会把点击拖到区域正中，纯粹是伤害；
  带贴到区域上/下边界 ⇒ 行被截断，中心不可信。

### 两个实测踩到的坑

1. **行分隔线被当成「行」**：1px 分隔线横贯整行，前景像素很多，投影出来就是一条带。
   吸到它上面等于点在两行交界处，**比不吸还糟**。用 `SNAP_BAND_MIN_SPAN=6` 滤掉。
2. **带边界算错**：原来在 `break` 时 `y` 已经自增过，`ymax = y - gap - 1` 会算出
   **ymax < ymin**（实测打印出「y 231~230，高 0px」）。改成单独跟踪 `last`。

### 行标尺（`_snap_core` 返回第 4 个值）

`refine_point` 现在会把本区域每条带的中心 y **按数字列出来**：

```
行标尺：本区域检测到 4 条横向内容带，中心 y = 240 / 287 / 317 / 364（屏幕物理坐标）。
⚠ 你给的 y 不在任何一条带上 —— 说明它落在两行之间的空隙里，这正是「点偏」最常见的原因。
```

这是解决「第几行」的**唯一可靠办法**：模型看图是**估**不出第几行在哪里的，而标尺是
**量**出来的。刻意只给**几何数字**（不含元素名、不含可点信息），不违背上一轮
「删掉罗列可点击元素」的决定 —— 它是一把尺子，不是一份元素清单。
配合 `space="screen"` 直接 `click(x, y_N, space="screen")`。

### 顺带的性能优化

连通域和行带原本各自构造一次前景掩码（区域放大到 176×176 后是纯浪费）。
抽出 `_fg_mask` / `_components_from_mask` / `_bands_from_mask`，`_snap_core` 里
**只构造一次掩码**共用：53.3ms → **38.6ms**。（`_fg_components` / `_fg_bands`
的原签名保留，测试不受影响。）

### 验证

- **真机**（真实抗锯齿像素，非合成）：在 WorkBuddy 侧边栏列表上检测到
  4 条带 y=240/287/317/364，工具调用列表上检测到 5 条带 y=379/419/455/495/532。
  估计点 (120,300) 正好落在**两行之间的空隙**里 → 警告如期触发、y 被修正到 287、
  x 保持不变。对照图人眼确认：黄准星在空隙、绿准星在行中心、像素锐利。
- **合成微信列表**：x=100/150/190/250 四个横向位置**全部**能对齐到正确行
  （修复前 x=190/250 是「完全不吸附」）。
- 测试 **111 个全绿**（101 + 10）。新增 9 个：行带检测（分隔线不算行）、
  **行内空白区仍能对齐 y 且 x 不动**（微信核心场景）、吸到行而非单个字、
  工具条 x 不被整带中心拽走、连续内容不得按带中心吸附、带内取最近候选、
  行标尺输出、y 落空隙的警告、确定性。
- 自检绿：23 个工具，6 个 endpoint 全 ok。`_snap_core` / `_snap_to_element` 等
  8 个函数全部就位，`declared == handled: True`。

### 注意

- **窗口枚举在本环境返回 0**（插件进程不在交互桌面上），所以没能直接在真的微信窗口上
  测；验证用的是**真机屏幕像素**（WorkBuddy 自己的列表）+ 合成微信列表。
- `dist/` 仍需重跑 `build_release.ps1`；源码方式运行需**重启程序**。
- 行标尺只覆盖当前搜索范围（默认上下各 88px，上限 140）。列表很长时先滚动到附近再量。

## 坐标精度第三轮：候选菜单 + 注入链路精确到 0 偏差（用户反馈「还是点不准」+「点微信联系人列表总是点偏」）

### 先量再改（关键方法论）
没动算法之前先把链路拆成独立可量的两段，分别量到 0 才动手：
- **截图对齐**：把区域平移 dx，用 SAD 求最优位移。1920 屏上 SAD 在位移 5px/11px 处
  **精确归 0**（曲线是清晰 V 形）→ `_region_snapshot_at` 的局部像素 ↔ 屏幕坐标 1:1 精确。
- **注入链路**：`_move_absolute(x,y)` 后回读 `GetCursorPos`。

### 发现并修掉的真 bug ①：鼠标注入归一化不是逆运算
Windows 把归一化值换算回像素用的是 `floor(nx * 屏宽 / 65536)`（本机 1920 宽屏**实测 80 个点
零误差验证**这个模型）。旧公式 `round(v*65535/(w-1))` 求逆方向不一致 → **1920 宽屏上有
7 个 x 系统性偏 1px**（1,2,3,8,9,16,23）。改为 `ceil(v*65536/span)`（整数 `-(-a//b)`，
对负值也正确，副屏在主屏左侧时差值为负）。
实测：旧公式 17 点合计偏 7px → **新公式 54 点（含那 7 个）全部 0 偏差**。
→ 教训：**归一化必须与目标平台的换算方向互为逆运算**，不能凭「round 最接近」拍。

### 发现并修掉的真 bug ②：`process_name` 一直是静默故障
AST 悬空名扫描抓到 `byref(pid)` 裸调用（模块只 `import ctypes`，没 `from ctypes import byref`）。
`process_name()` 外层 try 把 NameError 吞掉 → **每次调用都返回 `""`**，`list_windows`
每一行静默丢掉进程名。实测：前台窗口本该 `'WorkBuddyAI.exe'`，实际 `''`。
改 `ctypes.byref` + 装了两个回归测试（一个打桩验返回值，一个 AST 静态扫描防复发）。
→ 与上次「删元素工具时误删 `_join_notes`」同一类教训：**外层 try 会把运行时 NameError
变成静默降级**，必须靠 AST 扫描兜底，不能只看「模块能 import」。

### 核心算法改动：候选菜单（`refine_point` 的 `pick`）
诊断出真正的主因不是算得不准，而是**吸附只会挑「离估计点最近」的那一个** ——
按钮密排界面（Blender 工具栏 / 属性面板 / 一排小图标）上估计偏几像素，「最近的那个」
就是**隔壁按钮**，于是「点偏」变成「稳稳地点错」，且模型无从察觉。

新机制：`_fill_candidates()` 把区域内所有「像控件的目标」编号排出
（`kind` = 行[横向内容带] / 块[连通域]；每项带中心、尺寸、外接矩形、距离），
按距离排序取前 `SNAP_CAND_MAX=9`。`refine_point` 把它们**画成带编号的方框**
（青色=普通、洋红=选中，字号随放大倍数 16→32 缩放），并给出可直接照抄的
`click(x=…, y=…, space="screen", snap=false)`。
`pick=N` 可直接改选。**「估一个位置」变成「认一个编号」** —— 认出目标是模型擅长的，
算出目标在哪不是。依然只给几何数字，不违背「删掉罗列可点击元素」的决定。

配套：
- `_draw_box()` 新原语；`_capture_scaled`/`grab_zoom` 新增 `boxes=` 参数；
  连通行带现在也带 `xmin/xmax`（否则只能画通栏横线，编号无从谈起）。
- `click` 新增**落点回读**：回读 `GetCursorPos`，一致就报「0 偏差」，不一致就
  ⚠ 警告并提示先 `verify_point`。注入链路有偏差时不再静默点空。
- 放大图改为**以估计点为中心**（而非吸附点）—— 候选都在估计点附近，才都能收进画面。

### 验证
- 测试 **118 个全绿**（新增 8 个：候选菜单编号/排序/尺寸、改选编号、编号方框与洋红选中、
  归一化全量代数验证、落点回读、`process_name` 两个）。
- selftest 绿：23 工具、6 endpoint 全 ok。
- 真机候选菜单跑在侧边栏列表上：9 个候选 `1.行 2.行 3.块 …`，编号方框图人眼确认正确。
- 截图对齐 SAD = 0；注入链路 54 点全 0 偏差。

- `dist/` 仍是旧打包产物，需重跑 `build_release.ps1`；源码方式运行需重启程序。
