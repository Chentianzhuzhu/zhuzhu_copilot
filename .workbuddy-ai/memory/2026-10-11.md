## computer-control 插件：精确点击任意元素（深度优化）

**目标**：让 AI 能精确点击任意元素，例如「右键桌宠小猫 → 点退出」把它关掉。

### 关键实证结论（隔离探针逐一验证，勿凭直觉改）

- **UIA 树遍历的 vtable 索引**（猜错即段错误）：
  - `IUIAutomationTreeWalker`：FirstChild=**4**（不是 3）、NextSibling=6、Parent=3
  - `IUIAutomation` walker getter：14=ControlView / 15=ContentView / 16=RawView；
    ElementFromHandle=6、CreateTrueCondition=21
  - `IUIAutomationElement`：FindAll=6、GetCurrentPattern=**16**、ControlType=21、Name=23、
    Enabled=28、NativeHWND=36、Offscreen=38、BoundingRect=43
  - `IUIAutomationElementArray`：Length=3、GetElement=4
  - `IUIAutomationInvokePattern::Invoke`=3（所有 UIA 模式接口方法都从索引 3 开始）
- **UIA 控制模式 ID 用官方 UIAutomationClient.h 的值**（原代码表大面积写错）：
  Invoke=10000、Selection=10001、Value=10002、RangeValue=10003、Scroll=10004、
  ExpandCollapse=10005、Window=10009、SelectionItem=10010、Text=10014、Toggle=10015。
- **Qt（PyQt6）默认就会向 UIA 暴露内部控件**（Windows 按需激活，无需设
  `QT_ACCESSIBILITY`）：实测拿到 `Button:确定`、`Edit:`、`MenuItem:退出`。
- **QMenu 弹出菜单是独立顶层窗口**（类名如 `Qt6111QWindowPopupDropShadowSaveBits`），
  不属于触发它的窗口子树 → 对原窗口 list_elements 永远看不到菜单项。
- **PyQt 会把应用名自动设为窗口标题**（桌宠标题其实是 "python" / "zhuzhu Copilot"），
  所以「无标题」不能用来判浮层，要用 `WS_EX_TOOLWINDOW`（且非 `WS_EX_APPWINDOW`）。
- **桌宠就是本项目自己的** `src/zhuzhu_Copilot/ui/desktop_pet.py`：
  `FramelessWindowHint|WindowStaysOnTopHint|Tool`，右键 `QMenu`（回到右下角 / 退出）。

### 修掉的真实缺陷

1. `uia.py` 里 `PATTERN_SELECTION_ITEM` 未定义 → `Element.describe()` 直接 `NameError` 崩溃
   （真实调用路径必现）。
2. `_do_invoke` 里 pattern 接口对象被**重复 Release**（内层 finally + 外层 finally）
   → use-after-free，进程直接崩（exit 127）。
3. UIA 控制模式 ID 表大面积写错 → 元素能力误判。
4. `list_windows` 只列「有标题且 ≥60×40」的窗口 → 桌宠这类浮层完全不可见。
5. 元素工具用 `el.hwnd or 前台窗口` 定位归属窗口 → 自绘控件 hwnd=0 时会去激活错误的
   窗口、甚至把菜单弄关掉。改为几何归属判定（`_window_for_element`），且对菜单窗口
   **不做激活**（激活会把菜单关掉）。

### 性能

- 跨进程 UIA 调用约 1~2ms/次，大窗口全量读属性会到 3s+。对策：
  - `search_elements`：把 name/type 过滤**下推到遍历**，命中即停；
    剪枝时只读「名称+类型」两次调用，命中才付其余属性读取的代价
    （桌面 113 图标按类型检索 94ms，按名字 1.1s）。
  - 全量枚举受 `WALK_BUDGET_S=3.0` 时间预算约束；模式探测受
    `PATTERN_PROBE_MAX=160` + `PATTERN_PROBE_BUDGET_S=1.0` 约束。
- 未采用 CacheRequest 批量属性读取（需要额外未验证的 vtable 索引 + VARIANT/SafeArray
  解析，风险收益不划算）。

### 新增工具（TOOLS 27 个）

`inspect_point`（反查坐标点上的窗口/控件）、`click_window`（窗口相对坐标点击，
rel_x/rel_y 相对窗口左上角物理像素）、`list_menus`（列出弹出菜单及其菜单项）。
`click_element` 升级：可 Invoke 时**无坐标 Invoke**；原窗口找不到时**自动切到菜单窗口**。

### 验证方式

- `tests/test_computer_control_plugin.py` 新增 13 个用例（模式 ID 表、浮层分类、
  菜单识别、剪枝判定、命中测试、窗口归属、菜单自动切换、Invoke 优先/坐标回退、
  新工具注册、窗口相对点击越界保护）。共 54 个用例全绿。
- 端到端实跑（已清理临时脚本）：`list_windows` 发现桌宠浮层 →
  `click_window(button="right")` 呼出菜单 → `list_menus` 读出「退出」→
  `click_element(name="退出")` 自动切菜单窗口 + Invoke → 目标窗口消失。
- 注意：`tests/test_agent_plugin_context.py` 有 2 个失败，与本次改动**无关**
  （陈旧测试桩 `_Eng` 缺 `efficient_mode`，该文件 0 处涉及 computer-control）。

## computer-control 插件（第二轮）：面向 Blender 类生产级软件的精准鼠标点击

**目标**：Agent 必须能操控生产级复杂软件（Blender 这类），必须做到**鼠标精准点击**。

本机环境（实测）：**125% DPI 缩放**（物理 1920×1080 / 逻辑 1536×864）、**带触控数字化仪**、单显示器。
本机未安装 Blender（`C:/Program Files\Blender Foundation` 是空目录），因此自建靶场验证。

### 决定性实测结论（勿凭直觉改）

- **鼠标注入 vs 触控注入的精度（原生 Win32+WGL OpenGL 窗口，逐点核对目标窗口回显的客户区坐标）**：
  - 鼠标注入：偏差 **(+0,+0)** —— 像素级精准；
  - 触控注入：偏差 **0 ~ 428 像素且不可预测**（同一进程内多次 tap 的偏差方向与大小都不一致）。
  原因：触控要经过「数字化仪标定」+「触控→鼠标提升」两段坐标变换。
  → 结论：**默认必须走鼠标注入**，触控改为显式 `input="touch"` 才启用。
- **`PrintWindow(PW_RENDERFULLCONTENT)` 对 OpenGL 窗口通常可用**（DWM 合成），
  Qt 的 `QOpenGLWindow` 与原生 WGL 窗口实测都能抓到完整内容（含靶心像素数完全吻合）。
  但**屏幕区域抓取依赖窗口真的在最上层**（被遮挡时会抓到别的窗口）→ 只能当兜底，不能当首选。
- **PyQt 会把应用名自动设成窗口标题**（桌宠标题其实是 "python"），「无标题」不能用来判浮层。
- **`SetProcessDpiAwarenessContext(-4)` 必须显式调用**：不声明时进程是 DPI-unaware，
  `GetSystemMetrics(SM_CXSCREEN)` 返回逻辑尺寸（1536×864），窗口被系统按 1.25 缩放，
  `PrintWindow` 会返回「内容按逻辑尺寸渲染、放进物理尺寸位图」的错位图。

### 本轮修掉的真实缺陷

1. **多显示器绝对坐标缺 `MOUSEEVENTF_VIRTUALDESK`**：`_move_absolute` 用虚拟屏归一化
   0..65535 但没带该标志 → 0..65535 只映射主屏，副屏落点全错（本机单屏所以没暴露）。
   同时把 `int()` 截断改成 `round()`。
2. **触控优先的默认策略**（见上）→ 改为鼠标优先。
3. **`click_window` 的 `rel_x/rel_y` 语义有歧义**（窗口外框 vs 客户区），且窗口截图被缩放
   （宽 >1280 会等比缩小）时会整体偏掉 → 统一为「窗口截图上的像素坐标」，并按截图缩放比换算。
4. **空图误判**：一开始把「99.5% 同色」一律当空白，会把 Blender 的深色主题（#303030=48）
   误判 → 改为只有「近黑(<8) 占 98%+」或「同色且近黑(<24)/近白(>240)」才算空白。
5. **点击生效校验漏检**：12×12 稀疏采样采不到 2px 宽的标记线（实测误报「没生效」）→
   改为落点周围 96×96 的**逐像素比对**（36KB，约 1ms）。
6. **纯查询工具会开启操控会话**：`screen_info`/`screen_shot` 等只读查询也调用了
   `_touch_session()`，导致用户在 AI「只是看一眼」时随手动一下鼠标就被判成「用户接管」，
   之后所有点击被拒绝（真实误伤）→ 改为**只有 `_CONTROL_TOOLS` 里的真正操控动作才开启/续期会话**。
   （顺带修掉了 `test_mcp_calls_are_readonly_safe` 的偶发失败。）

### 新增能力

- `verify_point(x, y, move=true)`：精度自检 —— 换算物理坐标 + 移动光标 + 回读真实落点 +
  报告该点上的窗口/控件，偏差为 0 才算坐标链路精确。
- `click`/`click_element`/`click_window` 增加 `verify=true`：点击前后逐像素比对落点附近，
  直接报告「界面已响应」或「完全没有变化，别盲目重试同一坐标」。
- `screen_shot` 增加 `capture=auto|printwindow|screen`；`grab_window` 自动检测空图并兜底到屏幕抓取，
  返回文本里如实标注用了哪条路径。
- `input=auto|mouse|touch` 参数（click 系/long_press/drag/swipe/select）。
- 工具总数 28。

### 验证方式

- 靶场：自建 `原生 Win32 + WGL OpenGL 窗口`（无 WM_PRINTCLIENT、无子窗口、无 UIA 树、
  PerMonitorV2），在收到左键时回显客户区坐标并画十字标记 —— 用来客观核对落点。
- 端到端实测（已清理临时脚本）：
  - `verify_point` → 偏差 (+0,+0)；
  - `click` 靶心 A → 靶场收到客户区 (210,160)，偏差 (+0,+0)，verify 报「121 个像素变化，界面已响应」；
  - `click_window` 靶心 B → 客户区 (410,310)，偏差 (+0,+0)；
  - `grab_window` → PrintWindow 正常；`capture="screen"` 也可用。
- 测试：`tests/test_computer_control_plugin.py` 增至 **64 个用例全绿**（新增 10 个：
  注入方式解析/默认鼠标契约/VIRTUALDESK/空图判定/逐像素比对/截图兜底/verify_point×2/会话契约）。
- 注意：`tests/test_agent_plugin_context.py` 有 2 个失败，与本次改动无关（陈旧桩 `_Eng` 缺 `efficient_mode`）。

## computer-control 插件（第三轮）：真实任务实战——微信 登录→文件传输助手→发消息

**背景**：用户反馈「AI 用触控点击精度仍然很差，打开微信→点登录→点文件传输助手→发消息
这种基础任务都无法完成」。

### 先说结论：任务已跑通

用改造后的插件代码**真实完成**了整条链路（消息已发到文件传输助手，截图确认 18:56 的绿色气泡）：
`list_windows` → `list_elements(登录窗口)` → `click_element("进入微信")` → 用户手机扫码 →
`list_windows`（**主窗口 hwnd 变了**）→ `screen_shot(mode="window")` → 读出「文件传输助手」行的
像素位置 → `verify_point`（偏差 0）→ `click(x,y,verify=true)` → 点输入框 → `type_text` → `enter`。

### 关键实测事实（重要，勿凭直觉改）

1. **运行中的程序加载的是 `src/` 那份**（以 `python main.py` 起），但**改动需要重启程序才生效**；
   `dist/zhuzhu Copilot/` 是 PyInstaller 打包产物（旧代码，本轮改动 0 处命中）→ 发版前要重新打包。
2. **微信 4.x（`Weixin.exe`，Qt）**：
   - **登录窗口暴露完整 UIA 树**（26 个元素），按钮真实文字是 **「进入微信」而不是「登录」**；
   - **主窗口不暴露元素树**（只有 1 个元素，子窗口是 1×1 辅助窗口）→ 主界面只能坐标点击；
   - 登录需要**手机扫码**（安全边界，不可绕过）。
3. **UIA Invoke 会「假成功」**：微信「进入微信」按钮支持 Invoke、Invoke 返回成功、按钮甚至拿到焦点，
   但界面毫无变化（应用不执行点击逻辑）。**真实鼠标点击才生效**（点了之后跳到扫码界面）。

### 本轮修掉的 4 个真实缺陷（都是让基础任务失败的直接原因）

1. **截图能穿透遮挡，鼠标点击不能**（最致命）：
   窗口截图走 PrintWindow，**被遮挡也能截到内容**；鼠标点击只落到**该点最顶层窗口**上。
   于是「照着截图点」时点击全打到遮挡窗口上（微信窗口被 WorkBuddy 盖住时，我甚至误点了
   WorkBuddy 一下）。`click_element` 本来会激活窗口，但 **`click`/`drag`/`swipe`/`select`
   这些坐标工具不会** → 新增 `_ensure_click_target`：坐标点击前判断落点是否属于「最近一次
   窗口截图的那个窗口」，不是就先激活置顶（常规置顶被前台锁拒绝时改用**临时置顶**
   `HWND_TOPMOST→HWND_NOTOPMOST`，topmost 不受前台锁限制），两步都失败则**如实告警**。
2. **元素归属窗口用几何猜** → 改为「**在哪个窗口里找到的，那个窗口就是它的归属**」
   （`_pick_element` 现在返回 `(el, note, owner_hwnd)`）。此前微信登录窗口被遮挡时归属被猜成
   桌面 `Program Manager`，激活错窗口导致点击全落空。
3. **生效校验误报**：只看落点周围 96×96 小块，而点击副作用常发生在别处（点聊天行改变的是
   右侧会话面板）→ 改为**双通道**：局部逐像素 + **整窗指纹**（`_window_sig`：PrintWindow +
   StretchBlt 缩到 32px 宽再取样，跨进程只读 4KB）。现在会报「落点附近 6240/9216 像素变化、
   窗口整体变化 34%，界面已响应」。
4. **重叠候选逼模型猜 index**：微信按钮是 `Button 进入微信` + 内部 `Text 进入微信` 两个元素、
   中心完全重合 → 新增 `_dedupe_candidates`：中心相差 ≤3px 的候选合并，保留可操作性最高者
   （可 Invoke > 非 Text > 面积大）。另外「找不到元素」的报错现在会**列出该窗口所有可点击
   元素的真实标签**，模型一次就能改对名字。

### 给用户的关键结论

- 之前的失败**不是"触控"的问题**（本轮已把默认改成鼠标），而是上面 4 个缺陷；
- 触控偏差的结论仍然成立：本机鼠标注入 (+0,+0)，触控 0~428px 不可预测；
- **需要重启 zhuzhu Copilot**（源码方式运行）新代码才生效；打包版要重新构建。

### 验证

- `tests/test_computer_control_plugin.py` 增至 **67 个用例全绿**（本轮新增：
  `_dedupe_candidates` 合并、`_ensure_click_target` 激活/不越界、Invoke 假成功自动回退真实点击）。
- 连同 context_budget/agent_plugins/agent_mcp 共 **97 个用例全绿**。

## computer-control 插件（第四轮）：修复「文字发错应用」的致命缺陷

**用户反馈**：窗口被遮挡时，Agent 用「只截该窗口」的截屏方式，结果把输入信息发到了
**Agent 应用自己的输入框**里，而不是微信的输入框。

### 根因

**`SendInput` 的键击没有目标概念，只发给当前前台窗口。**
`type_text` / `key_press` / `copy` / `paste` 全都没有「目标窗口」意识 —— 点击若没能把焦点
交给目标窗口（被遮挡时很容易发生），随后的输入就进了当前前台应用。这是最危险的一类失败。

### 修法（已真机验证）

1. **新增 `_ensure_input_target(args, action)`**：每次键盘注入前确保目标窗口在最前
   （目标 = 显式 `title`/`hwnd`，或最近一次窗口截图的那个），抢不到焦点就**直接拒绝执行**
   并说明当前前台是谁 —— 绝不「先打了再说」。
   `win` 开头的系统级快捷键（如 win+ctrl+d）不受此约束。
2. **`_ensure_click_target` 改为「抢不到前台就拒绝点击」**（原来是警告后照点）：
   照点会点到遮挡窗口上，可能误触别的应用（比如「删除」「发送」）。宁可点不到。
3. **返回值如实报告「注入时前台窗口：X」**，让模型/用户立刻能核对文字去了哪里。
4. `type_text` / `key_press` / `copy` / `paste` 的 schema 补 `title`/`hwnd`。

真机验证：微信被 WorkBuddy 遮挡时调用 `type_text` → 返回
「已输入 6 个字符（注入时前台窗口：「微信」）」，截图确认文字确实进了**微信**的输入框
（而不是 Agent 的输入框）。

### 顺带发现并修掉的隐蔽缺陷

- **`_com_init` 把 `S_FALSE` 当成失败**：`CoInitializeEx` 在「本线程已初始化过 COM」时返回
  S_FALSE(1)，这是正常结果。原来的判据只认 S_OK 与 RPC_E_CHANGED_MODE，于是**只要进程里
  任何别的库先初始化过 COM（PyQt / 剪贴板 / Shell API…），UIA 就被静默禁用**，
  所有元素级工具集体降级成纯 Win32。实测复现：显式先调一次 `_com_init()` 之后
  `automation()` 就返回 None。已改为接受 `(S_OK, 1, 0x80010106)`。
- **撤销上一轮的一个错误设计**：给 `type_text` 加的「整窗指纹比对」是**误报源** ——
  实测输入 1 个字符只让窗口指纹变化 1~2 个采样点，与光标闪烁噪声同量级，据此报
  「没有变化」会害模型重复输入。已移除，改为只报告前台窗口。
- 也评估过用 UIA **Value 模式回读输入框内容**做校验，实测 Qt 的 Value 模式返回空串
  （不可靠），故放弃；元素级输入框的校验仍以截图为准。

### 验证

- `tests/test_computer_control_plugin.py` 增至 **71 个用例全绿**（本轮新增：
  `_ensure_input_target` 四场景（已在前台/能切过去/抢不到拒绝/无目标不约束）、
  `type_text` 被拒时零注入、`_ensure_click_target` 抢不到前台必须拒绝、
  COM S_FALSE 视为成功、COM 重复初始化幂等）。
- 连同 context_budget/agent_plugins/agent_mcp 共 **101 个用例全绿**。

## UI 调整：输入框缩短 + 模型下拉加宽

**需求**：把输入框长度缩短，模型选择下拉菜单加长。

**改动**（`src/zhuzhu_Copilot/ui/agent_panel.py`，输入行 `model_combo`）：
- `setMinimumWidth(150) → 260`，`setMaximumWidth(230) → 340`。
- 输入框 `self.input` 是 `stretch=1`（自动占满剩余空间），所以下拉加宽后输入框自动变短，
  不需要给输入框设 maxWidth（设了反而会在行尾留空隙 —— 该行没有 addStretch 收尾）。

**根因（为什么原来模型名被截断）**：
下拉内容区 = 宽度 − 左右内边距(2×SPACING_MD=24) − 箭头(COMBO_ARROW_W=22) − 图标与文字间距(≈22)。
150px 只剩 **82px** 给文字，实测 `agnes-2.5-flash` 显示成 `agnes-2.5-fla`。
另外 QComboBox 默认的 `AdjustToContentsOnFirstShow` **只在首次显示时按内容定宽**，而模型列表是
之后由 `_sync_model_combo()` 才填充的 → 宽度永远停在 minimumWidth 上（这点写测量脚本时必须复现，
否则量出来的宽度会偏大）。

**实测宽度（行宽 925px，从运行中界面截图量得）**：
| | 输入框 | 模型下拉 | 文字可用 |
|---|---|---|---|
| 改动前 | 633px | 150px | 82px（截断） |
| 改动后 | 523px | 260px | 192px（完整） |
即输入框 **−110px**、下拉 **+110px**。

**验证**：对比图见 `outputs/输入行宽度对比.png`（忠实复刻下拉的内边距/字号/箭头宽度渲染）。
相关 UI 测试 64 个全绿（input_row_affordances / dock_layout / brand_icons / design_tokens /
token_stats_popover）。

## computer-control 插件（第五轮）：让「第 N 个」「发文件」这类复合任务做准

**用户反馈**：复杂任务精度仍不够，例如「打开微信，把桌面上的某某文件发给微信第 xx 个人」。

### 拆解出的两个精度薄弱点

1. **「第 xx 个人」** —— 微信主窗口**没有可访问性树**，列表项无法用元素定位，
   只能照着截图肉眼数行；视觉模型数行很容易错，而这类任务的成败就在这一下。
2. **「发文件」** —— 从桌面拖图标进聊天窗口要经过「悬停触发 → 拖动 → 落点命中」多个易错环节。

### 新增工具 `list_rows`（29 个工具）

把屏幕区域里的**列表行**切出来，返回每行序号 + **精确中心坐标**，并给一张把序号画上去的图。
于是「第 3 个人」变成「点第 3 行的中心坐标」，不再靠数。

- 算法：`_modal_bg` 取众数色估背景 → 逐扫描线统计「与背景明显不同的像素占比」→
  连续内容带合并成行 → 按 `min_h`/`max_h`（默认 20~160px）过滤。
- **取图与 `screen_shot(mode="window")` 同源**（目标窗口的 PrintWindow）——这点是关键：
  第一版从屏幕抓，结果微信被编辑器盖住时把**编辑器的文字行**当成了聊天列表（实测复现）。
  同源之后既不受遮挡影响，又与 AI 所见图完全一致。
- 坐标换算：新增 `_phys_to_view()`（`to_physical` 的逆运算），行中心按**截图基准**返回。

**真机验证**：微信聊天列表切出 9 行（间距约 62px），标注图与真实行完全对齐
（#1 文件传输助手 / #2 微信ClawBot / #3 洲搭子2 …）；点「第 3 行」→ 精确选中**洲搭子2**
（截图确认绿色高亮 + 右侧打开对应会话）。
证据图：`outputs/行检测-微信聊天列表.png`、`outputs/行检测-点第3行结果.png`。

- **点「第 N 个」**：`screen_shot(window)` 圈区域 → `list_rows` 拿每行中心 → 对照标注图确认 → `click`。

## computer-control 插件（第六轮）：「还是无法精确点击目标用户」的根因修复

**用户反馈**：上一轮加了 `list_rows` 之后，仍然「无法精确点击目标用户」—— 同一种任务，
同一张截图，不同次运行点中的人不一样。

### 两个真正根因（都是「行号不稳定」的表现，与遮挡无关）

1. **行号随「圈选区域」漂移**：实测把区域顶边从 y 往里收 20px，「第 3 行」的中心就从 **y=242**
   跳到 **y=307**（整整差了一个人）。根因有三层：
   - (a) **绝对阈值被竖向分隔线污染**：旧逻辑「内容像素占比 > 5%」就当内容行，而微信每行右侧
     有条竖向分隔线 + 头像，空行也会被算成内容，边界行被切开。
   - (b) **选中行背景差异把阈值顶爆**：旧逻辑取 `p90` 做阈值，而「当前选中行」背景色与别的行不同
     → p90 被推到 320+，于是把所有行**合并成 1 个超大行**，行号彻底乱掉。
   - (c) **被切掉的边缘残行**：圈选区域顶部/底部常切到半行，半行被判成独立行，序号全错位。
   - **修法**：
     - 阈值改**百分位法**：`base = 排序后的 p20`（落在行间隙上）、
       `thresh = base + max(6, int(0.15*(p75 - base)))`，**不再用 p90**（避免选中行背景差异放大）；
     - **丢弃被切掉边缘行**：若首条内容带顶部 ≤2px 且其高度 < 中位高度 0.6 倍，视为残行丢弃；
       `tool_list_rows` 返回里带 `clipped` 列表，文本里打 ⚠ 提示「区域边界处有被切掉的不完整行」。
     - `pad`（默认 28px，**只上下留白**）让模型估的边界差几像素也不会切进行里。
   - **验证**：区域顶边在 y1=80~125 之间任意取值，「第 3 行」稳定落在 **y=242**（不再漂移）。

2. **最小化窗口的截图是「废图」**：最小化时窗口矩形是哨兵值 `(-32000, -32000, 160, 28)`，
   `PrintWindow` 仍然「成功」返回一张图，但里面全是垃圾，且据此算出的坐标**落在屏幕外**
   （-32000 附近）→ 点不到任何东西，还不会报错。
   - **修法**：新增 `_ensure_window_capturable(hwnd)`：最小化时自动 `ShowWindow(SW_RESTORE)` 恢复；
     恢复后矩形仍是哨兵值就**明确拒绝**（不再假装成功）；`grab_window` / `screen_shot` 都会先调它，
     返回文本如实标注「窗口已恢复」或「无法截图」。
   - SKILL.md 新增「坑 1.8」：若 `list_windows` 里某窗口只有 160×28、位置在 -32000 附近，
     就是最小化状态，先恢复再操作。

### 验证

- 端到端真机：微信聊天列表点「第 3 行」→ 精确选中 **洲搭子2**（截图确认绿色高亮 + 右侧对应会话）。
- `tests/test_computer_control_plugin.py` 增至 **82 个用例全绿**（本轮新增：
  `_detect_rows` 百分位阈值抗选中行离群、边缘残行丢弃、`_phys_to_view` 逆运算、
  `_ensure_window_capturable` 最小化→恢复、哨兵矩形拒绝、list_rows 注册与查询归类）。

## 新功能：Agent 语音输入（科大讯飞语音听写 IAT）

**需求**：接入讯飞语音识别作为 Agent 的语音输入；麦克风按钮放输入框右侧；
识别期间输入框上覆盖**蓝色渐变遮罩**，并**随说话音量波动闪烁**。

### 新增文件

- `src/zhuzhu_Copilot/core/agent_asr.py`（新，约 740 行）：凭据管理、HMAC-SHA256 鉴权、
  winmm 录音、双协议会话 + 自动降级。凭据存 `data_root()/agent/asr.json`。
- `scripts/verify_voice_input.py`（新）：离屏验证 + 截图（`ALL PASS`）。

### 决定性实测结论（勿凭直觉改）

1. **同一个 APPID 通常只开通一条线路**，两条协议信封/错误码完全不同：
   - `llm`（大模型版）`wss://iat.cn-huabei-1.xf-yun.com/v1`，信封 `header/parameter/payload`，
     结果在 `payload.result.text`（base64 包 JSON）；未开通返回 **11201 licc failed**。
   - `legacy`（经典流式版）`wss://iat-api.xfyun.cn/v2/iat`，信封 `common/business/data`，
     结果在 `data.result`（纯 JSON）；未开通返回 10404/10163。
   - **本账号是 classic 线路**（llm 报 11201）→ 因此做了 `PROTOCOL_SPECS` 双协议 + 自动降级，
     首次成功的协议写回 `asr.json`（`{"protocol": "legacy"}`）下次直接命中。
   - **经典版不接受 `business.result` 子对象**（实测 10163 unknown field）→ 该字段只能给 llm 版。
   - 鉴权两版**完全相同**：`host: {host}\ndate: {date}\nGET {path} HTTP/1.1` 做 HMAC-SHA256；
     日期用 `format_date_time(mktime(now.timetuple()))`（RFC1123）。
2. **APISecret 第 8 位是小写 `l` 不是大写 `I`**：截图分辨率低导致 OCR 误判，报 401
   `HMAC signature does not match`。把图放大 5× 后 base64 解码两种候选，真实值解出干净十六进制
   `102d9f76dc142bd1537a5896` → 确认是小写 l。
3. **`waveIn*` 的回调里绝对不能调用其他 wave 函数**（MSDN 硬约束）：回调只负责把数据塞进队列，
   由**独立的 feeder 线程**重新装载 buffer（`BUFFERS = 8`）。
4. **必须先开麦、后握手**：WS 握手实测要 **1.2s** 出头（打时间戳复现：`connecting` 在 0.006s、
   `recording` 在 1.243s），等握手完再开麦会把用户说的头一两个字整段丢掉。
   改为麦克风帧先进**有界队列**（`maxsize = 10s/40ms`），握手成功后一次性补发。
5. **首帧必须携带音频**（官方 demo 如此）：用空音频开帧会被判参数/数据异常。
   收尾时若用户**全程没开口**，也要发一次开帧 —— 但**不能发零长音频**
   （服务端回错误码，而此时 `got_ok` 仍为 False，会被误判成「该协议未开通」去换协议重试，
   用户什么都没说却收到「语音识别失败」）→ 改发一帧 `b"\x00" * FRAME_BYTES` 静音。
6. **`pgs == "rpl"` 的动态修正必须就地替换**：用 `rg=[起,止]` 替换区间历史段，
   若「先删再追加」被修正的内容会跑到句尾、语序全乱 → 段列表用**有序 list**（不是 dict）。
7. 讯飞返回的是**全量文本**，因此回填输入框是「录音开始时的原文 + 已识别文本」**整段覆盖**，
   不是追加。

### 遮罩视觉（`_VoiceOverlay`，作为输入框子控件，不进布局）

- 子控件 + 每帧 `_sync_geometry()` 贴合父控件：录音中输入框可能因多行内容被拉高，
  用布局会和输入框自身的 `_auto_height` 打架。`WA_TransparentForMouseEvents` 保证不挡输入。
- 音量按**快起慢落**平滑（`ATTACK=0.55` / `DECAY=0.09` / `FPS=33`）；直接用原始音量会
  逐帧生硬跳动，看起来像故障。
- **修掉两个真实视觉缺陷**（截图放大后复现）：
  - (a) 线宽固定 1.8px 而透明度不随音量衰减 → 轻声时振幅塌成 ~2px 的**水平直线**却仍以
    alpha≈136 全亮画出，像一道横穿输入框的**故障亮线**。改为**透明度 ∝ 音量** +
    振幅门槛（`amp > height*0.06` 才画）。
  - (b) 单一正弦看起来是「装饰波浪」不是人声 → 改**三组谐波叠加 + 两端收窄包络**
    （`env = sin(t*pi)`）。
- 整体压在半透明区间（峰值约 0.5 不透明度），保证识别出的文字能透过遮罩读清。
